# README 版本同步点：是否进发布自动化（方案稿，2026-10-03 凌晨）

> 呈报对象：总控/用户晨间裁决。背景：夜批14 W2 开工时发现 README「当前版本」与
> 三处下载直链仍为 0.1.0，而 v0.1.1 已于 2026-10-02 07:53 发布为 Latest——
> **首装学生被指去下载旧版约 12 小时**，属真实发生过的失效模式，不是假想风险。
> 本稿只做方案分析与建议，不改产品代码（`scripts/**` 不在本包恰域）。

## 问题面：README 里有五处版本耦合字符串

1. 「当前版本 **X.Y.Z**」（第 7 行）
2. 三步开始的 `CourseLens-X.Y.Z-setup.exe` 文件名
3. 《校验单》直链（`releases/download/client-vX.Y.Z/CourseLens-X.Y.Z-checksum.txt`，URL+文件名两处）
4. certutil 示例命令里的安装包文件名
5. 两处《Windows 安全提示图文指引》直链（tag `client-vX.Y.Z`）

漏改任意一处，学生都会在「核对快递单号」的关键步骤被带到错的文件名——
恰好是信任仪式最重要的那一步。

## 现有控制（本批已落）

- **侦探控制**：`tests/test_security_doc_contract.py::test_readme_version_matches_canon`
  现已覆盖全部五处（本批补强：原先只钉「当前版本」一行，现已逐个校验
  `CourseLens-X.Y.Z-` 与 `client-vX.Y.Z/` 字符串与 `courselens-version.json` 正典一致）。
- **过程控制**：`docs/release-checklist.md` 新增「每次发版站立项」（本批追加）。

## 方案对比

### A. 维持手动+钉（现状地板）

- 优点：零新机制；README 保持纯静态文件（GitHub 渲染友好）；发布管理员对措辞有完全裁量。
- 缺点：**失效模式已实锤发生一次**；检测延迟取决于下一次全量何时跑；五处靠人记。

### B. 一键同步脚本+钉（推荐）

- 形态：`scripts/sync_readme_version.py`（约 50 行 stdlib）：读
  `courselens-version.json`，把上列五处逐一改写为正典版本，改完自校验；
  发布管理员在发版清单里执行一次，契约钉做最后守门。
- 优点：把「记住五个地方」降为「跑一条命令」；零新外写面；README 仍是人写人读的静态文件；
  脚本与钉互为冗余（钉的结构断言同时守护脚本本身的时效性）。
- 缺点：仍是人工触发（但清单+钉双层兜底）；README 结构大改时脚本要跟着改（钉会先红）。
- 成本：一个小实现包（scripts+单测，半天内）。

### C. README 版本无关化（删「当前版本」与具体文件名）

- 优点：永不陈旧。
- 缺点：certutil 校验步骤需要确切文件名，删掉具体文件名=学生要自己替换命令里的名字，
  在最需要「照着敲」的一步加了智力门槛；「当前版本」也是一眼可信度信号。
  与北极星（真实学生视角、降低信任仪式摩擦）相悖，**不建议**。

### D. 发布链全自动改 README（pipeline 直接 commit main）

- 缺点：发布管道获得对源仓 main 的写面=新的信任边界；draft-then-publish 的
  人工裁量环节被绕过；为五个字符串引入发布链复杂度，收益不成比例。**不建议**。

## 建议

采 **B**：晨间派一个小实现包落 `scripts/sync_readme_version.py`（含单测），
发版清单站立项加一行「跑同步脚本」；A 的钉与清单保留作双保险。
C/D 否决理由如上。若总控倾向不新增脚本，则 A 现状已比事发前强一个量级
（五处全钉+清单站立项），可接受为长期态。
